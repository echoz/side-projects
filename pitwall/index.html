Bring your phone.

The planned watch-to-server path requires a paired phone with internet access. Phone-free use is not supported.

Updates can lag.

Watch upload intervals, phone and network delays, and client delivery affect what you see. Near-live is the goal; update latency is not guaranteed.

Simulator testing first.

HR/speed passed Garmin simulator tests. Richer activity data passed local server/client tests, but currently exceeds the watch simulator’s memory limit. That needs fixing before rich uploads are ready. Physical watch and phone delivery, including HTTPS access, remain unverified.

Three software components. A phone in the middle.

Watch → phone → server → terminal

  1. 01 / ON THE WATCH

    Transponder

    A Garmin Connect IQ data field that samples activity measurements and observes timer, lap and workout callbacks alongside native activity recording. The intended upload path uses your paired phone. Use one large field for the measurements; smaller slots show upload and acknowledgment status only.

    Connect IQ / Monkey C
  2. 02 / ON YOUR SERVER

    Pitwall daemon

    A Linux daemon packaged with the CLI and TUI in one Docker image. It saves readings to SQLite before acknowledging uploads; a persistent volume keeps data across container replacement.

    Docker / SwiftNIO / SQLite
  3. 03 / AT THE WALL

    CLI / TUI

    An agent-friendly CLI and a Chio terminal interface for measurements, activity context and delivery health. Poll or receive server-pushed snapshots locally, or run the client over SSH.

    Scriptable CLI / Chio TUI

Reading the measurements

Missing is different from zero.

Absent measurements stay absent. Failed reads stay visible. Every view keeps source age and delivery status visible. Swimming describes the previous interval or length; gear readings do not prove sensor connectivity. A last-observed recovery split does not prove the athlete is still recovering. Silence never means a workout finished.

03 / Current capabilities and limits

What works today.

Synthetic activity data flows through the local server into the CLI and TUI, including six additional context views. HR/speed has end-to-end Garmin simulator evidence. Rich watch uploads currently run out of memory in the simulator; reducing their memory use is the next step. Available fields depend on the activity, navigation and sensors. Physical workouts and races have not been validated.

NEW
VERIFIED / LOCAL SERVER + CLIENTS

See more of the workout.

The overview keeps cadence, power, distance, timer state, elevation, GPS, heart-rate zones, battery and upload health alongside heart rate and speed. Last-observed timer, lap, workout and split events add context. Six additional views cover activity summary and profile, navigation, pressure, effort, swimming and cycling. This is sampled context, not a complete event history; Garmin blocks native workout-step names, targets and repeat numbers from data fields.

Summary includes native averages, maxima, calories, start time/location and the activity profile identifier. Navigation includes bearings, course deviation and destinations. Pressure keeps ambient, raw and sea-level readings distinct. Effort includes oxygen saturation, estimated energy expenditure and aerobic Training Effect. Swimming shows the previous interval or length; cycling shows observed front and rear gears. Availability varies by sport, device and sensors.

01
VERIFIED / SIMULATOR + LOCAL

Five-minute simulator workout

A five-minute Forerunner 970 simulator run plus final checks delivered 306 consecutive synthetic HR/speed samples into SQLite. Lost acknowledgments retried safely. Both server-pushed CLI / TUI clients recovered after a daemon restart and kept showing advancing readings.

02
MEASURED / LOCAL SIMULATOR RUN

Server-pushed updates

The CLI observed 42 of 42 batch snapshots in the timing window. Local upload-to-CLI timing: median ≈47 ms; 95th percentile ≈91 ms, including test observation delay. Watch batching, phone transport and TUI screen rendering are outside this measurement. These results describe one local run, with no latency guarantee.

03
VERIFIED / LINUX DOCKER

Run the server in Docker

One image includes the daemon, CLI and actual Chio TUI. Private readings and credentials survive container replacement. Run clients inside the container, using SSH to reach your server. The current package exposes no network ports; phone HTTPS access is still to come.

04
VERIFIED / LOCAL SERVER

Back up and restore readings

Stop the daemon, create a private backup, and restore into a new directory. Readings, original receipt times, upload retry records and credentials are preserved. A live CLI can reconnect to the restored state. Backups contain active credentials and are not encrypted; scheduled and online backups remain planned.

05
LATER / PHYSICAL VALIDATION

Validate the watch and phone

Physical testing is deferred. Later, validate a Forerunner 970 and iPhone bridge, including locked-phone delivery, interruptions, native recording and battery impact. Phone-reachable HTTPS is not yet implemented or verified.

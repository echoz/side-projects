Three software components. A phone in the middle.

Watch → phone → server → terminal

  1. 01 / ON THE WATCH

    Transponder

    A Garmin Connect IQ data field that samples activity measurements and observes timer, lap and workout callbacks alongside native activity recording. The intended upload path uses your paired phone. Every field size shows upload and acknowledgment status. Use Garmin’s native fields for workout measurements.

    Connect IQ / Monkey C
  2. 02 / ON YOUR SERVER

    Pitwall daemon

    A Linux daemon packaged with the CLI and TUI in one Docker image. It saves readings to SQLite before acknowledging uploads; a persistent volume keeps data across container replacement.

    Docker / SwiftNIO / SQLite
  3. 03 / AT THE WALL

    CLI / TUI

    An agent-friendly CLI and an F1-style Chio workout console with Running, Cycling and General layouts and visible data freshness. Separate views keep activity context and delivery diagnostics close by. Poll or receive server-pushed snapshots locally, or run the client over SSH.

    Scriptable CLI / Chio TUI

Supported uploads / Watch → service

What Transponder can send.

The telemetry service accepts these readings when Garmin provides them. The watch field shows delivery status; the uploaded data contains much more.

Availability varies by activity, device, navigation and sensors. Missing readings stay missing. Rich uploads are verified with synthetic data in Garmin’s simulator; physical watch and phone delivery remain unverified.

01Workout measurements
  • Heart rate, speed, cadence and power.
  • Distance, timer time, elapsed time and sampled timer state.
  • Elevation, total ascent and total descent.
  • Sport-specific heart-rate zone boundaries.
02Activity & summary
  • Activity profile name and identifier, sport and sub-sport.
  • Garmin’s average and maximum heart rate, speed, cadence and power.
  • Calories, activity start time and start location.
03Location & navigation
  • Latitude, longitude and Garmin’s GPS accuracy quality code.
  • Heading, bearing to destination, bearing from start and track angle.
  • Destination and next-point names, distances and elevations; off-course distance.
04Pressure & effort
  • Ambient, raw ambient and sea-level pressure as separate readings.
  • Oxygen saturation, estimated energy expenditure per minute and aerobic Training Effect.
05Swimming
  • Previous interval’s average stroke distance.
  • Previous length’s stroke type and SWOLF score.
06Cycling
  • Observed front and rear gears: gear index, maximum index and tooth count.
07Last-observed events
  • Timer start, pause, resume, stop or reset.
  • Lap notification and its trigger code; workout started or step completed.
  • Split start or end, type, distance, timer and elapsed time, ascent and descent, average and maximum speed.
  • Observation time and ordering for the latest event in each category, not a complete event history.
08Device & delivery
  • Watch battery, reported phone connection, firmware and Connect IQ versions.
  • Queued, dropped and rejected sample counts; time since the last upload acknowledgment.
  • Sample timestamps, ordering and source/session identifiers.

Phone connection and an earlier acknowledgment do not prove current delivery.

Calculated in the viewerPace comes from speed. The displayed heart-rate zone comes from heart rate and the uploaded zone boundaries.

Not supplied by the data fieldNative workout-step names, targets and repeat numbers. A timer stop or silence does not confirm a finished or saved workout.

Reading the measurements

Missing is different from zero.

Absent measurements stay absent. Failed reads stay visible. Every TUI view keeps source age and read status visible. Swimming describes the previous interval or length; gear readings do not prove sensor connectivity. A last-observed recovery split does not prove the athlete is still recovering. Silence never means a workout finished.

VERIFIED / SIMULATOR + LOCAL

Five-minute simulator workout

A five-minute Garmin simulator run against the Linux container delivered 278 rich synthetic samples into SQLite and accounted for 22 readings overwritten during deliberate interruptions. Batches awaiting acknowledgment stayed unchanged for safe retry. Fresh CLI and TUI sessions showed advancing readings after the container restarted.

02
MEASURED / LOCAL SIMULATOR RUN

Server-pushed updates

In the earlier HR/speed run, the CLI observed 42 of 42 batch snapshots in the timing window. Local upload-to-CLI timing: median ≈47 ms; 95th percentile ≈91 ms, including test observation delay. Watch batching, phone transport and TUI screen rendering are outside this measurement. These results describe one local run, with no latency guarantee.

03
VERIFIED / LINUX DOCKER

Run the server in Docker

One image includes the daemon, CLI and actual Chio TUI. Private readings and credentials survive container replacement. Run clients inside the container, using SSH to reach your server. The default Docker setup exposes no network ports; phone HTTPS access is still to come.

Local Mac testing keeps Garmin’s actual simulator on macOS and runs the Linux server, CLI and Chio TUI in Apple containers. This combined path now passes a five-minute workout with server-pushed readings, a lost acknowledgment and a server restart. Physical watch and phone delivery remain unverified.

Known issue: quitting the Linux TUI immediately after a resize has intermittently stalled in testing. The cause remains under investigation.

04
VERIFIED / LOCAL SERVER

Back up and restore readings

Stop the daemon, create a private backup, and restore into a new directory. Readings, original receipt times, upload retry records and credentials are preserved. A live CLI can reconnect to the restored state. Backups contain active credentials and are not encrypted; scheduled and online backups remain planned.

TRACK 01 / WORKOUT EXPERIENCE

Clearer progress. Deliberate reporting.

  1. First: activity-specific workout screens.

    Running prioritizes pace, heart rate, time and distance. Cycling prioritizes speed, power, cadence and heart rate. General covers other activities. Auto follows the reported sport; v selects a layout manually. Missing readings keep their slots. Wide, stacked and compact views are checked locally on macOS and Linux, with actual synthetic captures above.

    Heart-rate and battery gauges use observed values. Completion counts do not identify the current workout step. The earlier intermittent Linux resize/quit issue remains open. Hiking, swimming and strength screens are proposed; plans and trends need their own data contracts. Maps are deferred.

  2. Completion counts + Fixed cadence: qualification pending.

    The opt-in path counts captured workout callbacks and sends at steady 5/10-second slots. Server, storage and real CLI/TUI checks pass on macOS and Linux, including lost replies and visible count inconsistencies. All 54 Garmin SDK tests and the first five-minute production case pass: 10-second reporting with adversarial payloads and polling clients, including sampled memory checks. Seven other combinations and the final HTTPS-enforcement check remain pending. Counts do not identify native workout steps.

  3. Report significant changes.

    Schedule meaningful events with minimum spacing and periodic updates, without noisy readings causing a burst of uploads.

  4. Align manual or imported workout plans.

    Bono is a planned pure interpretation and advice component: it will use retained inputs, combining pinned plan revisions with observed completion counts. Pitwall owns source orchestration. Show current and next steps where supported; keep uncertain alignment visible.

  5. Adapt reporting locally with Auto.

    Use available battery and signal-quality observations with conservative fallbacks. The watch can adapt its reporting without remote advice.

  6. Add optional Bono reporting hints.

    After local scheduling is stable, Bono may suggest upload intervals. The watch owns the applied cadence and limits; reporting must remain useful when advice is missing, late or invalid.

TRACK 02 / OPTIONAL SOURCE PLUGINS

Add context without delaying telemetry.

  1. Contract ready. Process host follows the console.

    PitwallSourcePluginKit is a shared Swift contract library for immutable plugin messages, validation and pure response decisions, with no live I/O. Its synthetic fixtures pass on macOS and Linux, preserving missing values, dated daily context and provenance. The future host in Pitwall's daemon will own plugin launches, reads, deadlines, recovery and storage; it is not implemented yet.

  2. Read Blackbox's existing local daily summaries.

    Actual source plugins will be separate executables. The first planned plugin is a read-only adapter for context already available in the separate Blackbox project; it is not implemented yet. Blackbox's remote synchronization is currently disabled; planned-workout and completed-activity access need further contracts.

  3. Add providers and plans when access is verified.

    Investigate further sources against real access and supported contracts. Runna access remains unverified. Manual and imported plan work can proceed without a provider connection.

Plugins are optional. Missing or slow sources must leave watch uploads and the core workout view operational, with unavailable or stale context labeled.

Separate gates remain open. Protected local control, phone-reachable HTTPS, device provisioning and recovery remain ongoing work. Physical watch and phone validation is deferred; simulator results do not establish battery savings. The Linux TUI resize/quit issue remains under investigation.
